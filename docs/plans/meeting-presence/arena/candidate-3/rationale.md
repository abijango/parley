# Candidate 3 — Per-app `MeetingSource`

## Problem

Parley's meeting metadata is one procedure with app names hardcoded inside it. `MeetingMetadataResolver.scan` opens with `let isTeamsCall = …` / `let isZoomCall = …` and then branches five times: which window titles to read, which pids to walk, when to flip the Electron switches, which parser to call, whether to try a calendar. Everything it learns collapses into `DiscoveredMetadata { title?, titleSource?, roster: [RosterEntry] }`, and `RosterEntry` is `{ name, role? }` — a flat bag. That flatness is the reported bug: `teamsAttendees` walks the `AXOutline desc="Attendees"` subtree, skips the two section headers, and emits people from *both* "In this meeting" and "Others invited" as the same value, so the invite list and the people in the room are indistinguishable by the time `RecordingController.mergeRoster` sees them. `MeetingParsersTests.testTeamsAttendeesParsesRosterRows` asserts that behaviour, so the defect is load-bearing in the test suite. The flatness costs twice more: an empty roster means both "the People pane is closed" and "nobody is here", so the resolver suppresses empty readings and presence-now is unobservable; and `mergeRoster` stamps `firstSeen = Date()` at first sighting, which the UI prints as "joined 10:03" even when 10:03 is when the pane opened. Meanwhile Webex is invisible on both axes — it is not in `defaultConferencingBundleIDs` (so `known: false`, notify-only, display name "spark") and it has no resolver branch. Adding it to today's shape means a third `isWebexCall` and a sixth branch. Constraints the design must honor: recording never depends on AX or calendar; we never drive conferencing UI; EventKit is empty for this user and Graph is not a live-presence source; Webex selectors must come from a MeetingProbe dump, not from guesses; old `session.json` must decode; attendee names cannot contain commas; AX stays off the main actor and must have a messaging timeout.

## Usage (caller's view)

Written first, in [`usage.md`](usage.md), and the sketch is derived from it. In brief: a `MeetingSourcePoller` fires a timer and delivers `SourceReading { title: TitleCandidate?, roster: RosterSnapshot }`; `RecordingController` offers the title to the session, folds the snapshot into `meeting.roster`, and runs `AttendeePolicy.admissions` — about fifteen lines, none of which name an app. The inspector renders `AttendeePolicy.uncertainChips` and, separately and collapsed, `meeting.roster.invited`. Adding Webex is a new file plus one line in the registry array. Sources are tested by handing them a `RecordedUITree` built from a probe dump, with no AX and no main actor.

## Shape

**Data structures first.** Three types carry everything.

`Presence` is `.inCall(PresenceEvidence)` / `.left(at:)` / `.invited(InviteResponse?)`. Presence-versus-invited is the distinction the product needs, so it is a domain enum rather than a filter applied downstream. The Teams "Others invited" rows become `.invited`, and nothing further down can accidentally treat them as attendance.

`RosterCoverage` is `.unreadable` / `.sightings` / `.complete`, and it is the load-bearing field. It says *what the source's silence means*. `.unreadable` (Teams People pane closed, tree not built, budget blown) makes `apply` a no-op — absence proves nothing. `.sightings` (Zoom speaker tiles with the panel closed) is additive only. `.complete` (Teams Attendees outline, Zoom Participants panel) is the only coverage under which someone's absence marks them as `.left`. This single field replaces the resolver's "drop empty updates" hack and makes departure observable for the first time. `RosterSnapshot` is therefore always delivered, never suppressed.

`Arrival` is `.joined(at:)` / `.presentBeforeFirstSight(noticedAt:)` / `.neverObserved`, stamped once on the transition into `.inCall` and never rewritten. `RosterSnapshot.isFirstSighting` is what distinguishes the two present cases: everyone visible in the first readable snapshot may have joined long before we could see, so the UI says "in call", and only people who appear in a *later* snapshot get a clock time. The current "joined HH:mm" is a claim the data does not support; this makes the type refuse to make it.

`DisplayName` is a comma-free, non-empty validated name with a failable init that absorbs `stripStatusBadges` and `normalizeDisplayName`. Validation happens once at the parse boundary and every consumer downstream trusts the type, per `boundary-discipline` and `encode-lessons-in-structure`. The comma-delimited storage invariant stops being a comment in three files.

`TitleAuthority` is `.scheduleOverlap < .appContext < .callWindow`. Best-so-far wins, replacing the resolver's `titleLocked` first-wins rule, which can freeze a merely-overlapping calendar entry before the Teams call window has settled — a failure the how-critique consensus flagged explicitly. `TitleCandidate.provenance` keeps the existing `titleSource` strings, so manifests are unchanged.

**The module.** `MeetingSource` is one method: `read(ScanContext) -> SourceReading`. Behind it sits everything app-specific — which window is the call window, when to flip Electron switches, how often a whole-tree walk is affordable, which sibling app holds a rendered calendar, what a missing anchor means, whether an invite section even exists. `TeamsSource` alone hides the pipe-format title parse, the nav-view rejection, the generic-title retry, the once-per-pid Electron switches, the tick-3-and-6 calendar rationing, the even-tick roster cadence, the section split, and the pane-closed-is-unreadable rule. The caller sees a title and a snapshot. That is the interface depth argument: a one-method surface hiding the entire per-app story, and learning it saves the caller from learning any of it.

**The poller is a dumb clock.** It fires a timer, snapshots running pids on the main actor into `RunningApps` (NSWorkspace is not queue-safe), computes `ScanNeeds` from what it has already delivered, and dispatches to the source on the serial AX queue. It contains no bundle id, no app name, no parser, and does not change when Webex lands. `ScanNeeds.title` goes false once a `.callWindow`-authority candidate has been emitted or the ~16s give-up passes; the poller tracks only its own emissions, so there is no second copy of the title lock to keep in sync with the session.

**`MeetingSourceRegistry` is the single source of truth about conferencing apps.** `SourceIdentity` carries the display name, the bundle matchers, and a `SourceCapability`. `CallDetector`'s known-app set and its hardcoded display-name map are derived from it rather than maintained beside it. This is what makes Webex a two-line change: claiming `cisco-systems.spark` with `capability: .none` immediately makes it a known app (auto-record eligible, called "Webex" instead of "spark call") while its parsers are still `fatalError`. `known` and *metadata-capable* stop being the same fact, which the consensus named as a required split. Settings-added bundle ids still union on top and resolve to no source — detection only, exactly today's behaviour for an unparsed app.

**What is deliberately outside the sources.** `MeetingRoster` is a dumb value-type fold with no app knowledge and no product policy: upsert, stamp arrival once, mark absent-as-left under `.complete`, record decisions. `AttendeePolicy` is three pure functions holding the one product rule — auto-admit confident in-call people who look like people, chip the uncertain ones, list invited-not-joined separately and collapsed. Auto-admit routes through the existing `addAttendeeIfAbsent`, the same path speaker-ID already uses, so it is not a new writer, per `subtract-before-you-add`. `AttendeeDecision` makes admission idempotent: only `.undecided` people are ever acted on, so running the policy on every 2.5s tick admits each person exactly once and a dismissal is permanent, per `make-operations-idempotent`.

**Boundaries and what the design refuses to do.** `MeetingUITree` is the only capability a source receives, and it is structurally read-only — there is no method that presses, focuses, or navigates, so "never drive conferencing UI" cannot be violated by a source even by accident. `AXNode` stays the internal parsing vocabulary and never leaves the Detection module; `SourceReading` carries domain types only. `LiveMeetingUITree` sets `AXUIElementSetMessagingTimeout` and honours `ScanBudget.deadline`, so a wedged Teams or Webex cannot leak the AX queue. Nothing here touches recording, capture, or stop — the poller is a listener, and its total failure mode is `.unreadable` coverage forever.

**Call chain.** Source → snapshot → roster fold → policy. Three files from AX to attendee, per `minimize-reader-load`. `DiscoveredMetadata`, `RosterEntry`, `MeetingMetadataResolver`, `mergeRoster`, and the `isTeamsCall`/`isZoomCall` branching are all deleted.

## Tradeoffs accepted

- **We accept per-app duplication in exchange for per-app honesty.** Teams and Zoom will both contain "find the call window, walk it, parse it". Factoring that into a shared base class is exactly how the current `if isTeamsCall` ladder started; the duplication is the price of each source being able to state its own truth about coverage, cadence, and calendar surfaces without negotiating with a shared abstraction.
- **We accept that adding a source is a code change, not configuration,** in exchange for parsers that are typed, tested, and dump-driven. A selector-string config file would be smaller and would invite exactly the guessing the Webex constraint forbids.
- **We accept a Teams roster that is `.unreadable` whenever the People pane is closed** — no chips at all — in exchange for never again presenting the invite list as attendance. Silence is the honest answer until a tile-based Teams presence parser exists, and it is a strictly better failure than today's wrong answer.
- **We accept that `RosterCoverage` is per-snapshot, not per-app,** which looks like over-modelling until Zoom needs `.complete` with the panel open and `.sightings` with it closed within one call.
- **We accept auto-admitting people into `meeting.attendees`,** overturning the "suggestions never auto-enter attendees" invariant. That invariant was compensation for the bag: when you cannot tell an invitee from a participant, every automatic add is a guess. Once presence is a type, adding a `.inCall` person who looks like a person is not a guess, and dismiss is the undo.
- **We accept `@unchecked Sendable` on source conformances** in exchange for per-call mutable state with no locks, on the strength of serial-queue confinement. The alternative — actors — reintroduces suspension points inside a scan that is already bounded by a deadline.
- **We accept that `MeetingRoster` is a fold with no policy inside it,** which will look thin next to a ledger. Deliberate: sources are where complexity is concentrated in this shape, and a fold that knows nothing can be replaced wholesale without touching a single source.

## Alternatives considered

**Keep `MeetingMetadataResolver` as the deep module and make presence a parse distinction** (the smallest change: parsers emit present-versus-invited, everything else stays). It fixes the reported bug and nothing else. Interface depth: the public surface stays `DiscoveredMetadata`, so it hides no more than today, and every new app still costs a branch inside one `scan` function that already carries five. It also cannot express coverage without the resolver learning which apps have which surfaces — the app-specific knowledge simply relocates from the parser to the scanner. Rejected because Webex is a stated priority and this shape makes Webex more expensive, not less.

**A presence ledger owning first-seen, present-now, recommended, and accepted, fed by the existing resolver.** This is a genuinely good shape for the downstream half and it fixes the arrays-merged-forever problem. It loses because it fixes the wrong end: the ledger can only be as truthful as its inputs, and the inputs are the problem. A ledger fed by `RosterEntry` still cannot tell an invitee from a participant, still cannot tell a closed pane from an empty meeting, and still stamps pane-open time as a join. Its interface is also wider — a stateful object with admit/dismiss/recommend/present-now — while hiding less capability than a source does. The parts worth keeping (first-seen ownership, decisions living beside observations) are present here as `MeetingRoster` + `AttendeeDecision`, minus the policy.

**Auto-admit present people as the organizing idea, with the pipeline otherwise unchanged.** Correct as a product default and adopted as this design's policy, but it is a policy, not a shape. Stated as an architecture it has nowhere to put coverage, arrival honesty, or Webex, and it makes the auto-admit rule structurally dependent on parser output whose presence semantics are undefined — auto-adding from today's bag would silently file the entire Outlook invite list into `attendees`, which is strictly worse than the bug it is meant to fix.

**One `MeetingSource` with a data-driven per-app configuration** (anchor strings, window-title patterns, section names as data). Tempting because it makes Webex a config entry. Rejected: Teams' pane-closed rule, Zoom's two-surface coverage split, and Webex's in-call-versus-chat detection are logic, not strings, and encoding logic as configuration produces a config language nobody can test. It also directly violates the "do not invent Webex selectors" constraint by making invention cheap.

## Open questions and risks

- When Teams' People pane is closed for an entire call, this design shows nothing at all — no chips, no names. Is silence the right answer, or should the Record tab surface a one-line "open the People pane in Teams to suggest attendees" hint? A hint is the only non-coercive alternative to driving the UI, but it is also a nudge to change how the user runs their meetings.
- Auto-admit is scoped to `.inCall` people who pass `isLikelyPerson`. Should a `.left` person who was auto-admitted early and dropped off after two minutes stay in `attendees`? Keeping them is the current assumption (they attended), but a two-minute misjoin would persist into the note.
- `MeetingParsersTests.testTeamsAttendeesParsesRosterRows` currently asserts the defect. Rewriting it to assert the section split is straightforward, but is the existing 2026-06 probe dump rich enough to prove the "Others invited" split, or does that need a fresh capture before implementation starts?
- Deriving `CallDetector`'s known-app set from the registry changes behaviour for a user who has *removed* a default bundle id from Settings — the registry would silently re-add it. Should Settings store explicit removals, or is the registry set a floor?
- Webex ships as `capability: .none`, so it becomes auto-record eligible before any metadata works. Is a known app with no title and no roster a better or worse experience than today's notify-only, given the title will read "Webex call"?
- Zoom's `.appContext` title depends on the Workplace home window being open. If it usually is not, Zoom titles stay "Zoom call" and the authority ranking buys nothing there. Worth a probe before investing in the Zoom title path at all?
