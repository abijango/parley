# Candidate 3 — self-screen against `design-red-flags.md`

**Shallow module.** `MeetingSource` is one method, `read(ScanContext) -> SourceReading`, and `TeamsSource` alone hides the pipe-format title parse, nav-view rejection, the generic-title retry, once-per-pid Electron switches, tick-3-and-6 calendar rationing, even-tick roster cadence, the present/invited section split, and the pane-closed-means-unreadable rule. Learning the interface genuinely saves the caller from learning any of that — no caller can tell Teams from Webex. `MeetingSourcePoller` is the one module that is thin on purpose (a timer, a pid snapshot, a dispatch), and it earns that by being the file that never changes when a source is added; it is not a layer over a source's capability but the clock a source needs and should not own. `MeetingRoster` is also deliberately thin, and that is the honest weak point of this candidate: it is a fold, and if a reviewer wants a domain object that owns policy, this shape does not give them one. **Pass, with `MeetingRoster` flagged as the shallowest thing here.**

**Information leakage.** The presence-versus-invited decision lives in exactly one place per app — the source — and crosses the boundary as `Presence`, so no downstream module re-derives it from strings. The comma-free name rule is enforced once, in `DisplayName.init?`, instead of being re-checked in the parser, the merge, and the writer. The conferencing-app registry replaces two parallel lists (`defaultConferencingBundleIDs` and `CallDetector.displayName`'s hardcoded map) with one derivation. AX types are contained: `AXNode` stays the Detection module's internal parsing vocabulary and `SourceReading` carries only domain types, so no `AXUIElement`, node array, or window title reaches the controller or the UI. The one thing knowingly shared across the boundary is `TitleCandidate.provenance`, a stable string persisted as `SessionManifest.titleSource` — kept for manifest compatibility rather than re-derived, and paired with `TitleAuthority` so ranking never depends on parsing it. **Pass.**

**Temporal decomposition.** The shape is organized by *whose knowledge it is*, not by when it runs: Teams' knowledge lives in `TeamsSource` whether it is used at tick 1 or tick 40, and a source's title path and roster path share one object because they protect the same decisions about which window is the call window. The one axis that is time-shaped is `ScanContext.tick` / `ScanNeeds`, but those are inputs a source interprets with its own cost knowledge rather than stages the poller sequences — the poller never orchestrates "now parse, now merge". The scan→parse→merge sandwich the how-critique told us to refuse is gone: there is no merge stage, only a fold the session owns. **Pass.**

**Pass-through method.** `MeetingSourcePoller.start(for:)` is the closest call, since it forwards a `DetectedCall` toward a source — but it adds real policy (registry resolution, capability gating, trust and settings checks, needs computation, queue hop, budget) and changes shape from `DetectedCall` to `ScanContext`, so it is a boundary, not a forward. `RecordingController.admit` / `dismiss` each do two things the roster cannot do alone (record the decision *and* reconcile the comma-delimited `attendees` string), so neither is a bare forward. `MeetingRoster.record(_:for:)` is a one-line mutation, which is a forward in spirit; it stays because the roster owns the `people` array's invariants and exposing it mutably would leak them. **Pass, with `record(_:for:)` noted as the marginal case.**
